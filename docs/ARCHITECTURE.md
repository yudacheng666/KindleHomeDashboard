# 架构候选（待批准）
## 用户版
优先评估以现有 Home Assistant OS 为后端：采集、调度、数据、手机管理、备份和更新复用 HA；Kindle 专用灰度图优先使用 HA 内置运行的社区渲染集成，无需额外常驻容器。原独立后端方案降为备选，不视为已取消或已批准新架构。前提是核心公交和驾车数据源合规、免费额度足够且实际验证通过，基础天气免费可用。
## 技术路径
- 公交/驾车：正式 API → REST/REST command + 自动化及模板，简单配置优先；复杂签名、多个路线、额度、退避、错误处理及图形配置确有需要时才实现小型 HA 自定义集成。分时触发必须避免默认轮询叠加；核实最新成功采集时间、源数据时间及过期状态。
- 家庭：HA Local to-do / Shopping list；Local calendar 可录入每周菜单及循环提醒，calendar.get_events / todo.get_items 与模板实体供渲染。食材联动及周期待办的生成、去重、完成逻辑需少量配置或扩展，不默认新增菜谱服务器。
- 显示：优先验证 cryptomilk/hass-eink-dashboard（HA 内 SVG/resvg PNG，视觉编辑、中文字体、ETag、客户端拉取）；客户端恢复、分页、过期提示、电池/在线状态及15–30秒级屏幕更新仍需验证。该项目的图片端点无需认证，不能原样暴露至公网或不可信网络；先实现适合旧 Kindle 的只读访问保护，避免将 HA 管理凭证放在 Kindle。设备分辨率以实机为准。
- 管理：HA 仪表板、帮助器、集成配置向导、自动化与备份。更新优先用适配实际版本的 Marketplace（2026.11+）/HACS 或手工安装；先备份、检查兼容及回退，不强制升级现有 HA，也不自动更新 Kindle 固件。
## 资源与风险
目标新增常驻进程/容器为零，并非零内存/CPU；高频网络、渲染、日志和 recorder 写入应单独测量，排除无价值的高频实体历史，保护 HA 原有智能家居。自定义集成同进程运行，需审查依赖、非阻塞 I/O、失败隔离与版本兼容，避免影响主系统。若实际负载或隔离要求不满足，则使用独立轻量渲染/适配服务；不重复实现 HA 业务后端。必要时才考虑备用硬件。
