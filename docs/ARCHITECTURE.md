# 架构比较（未选定）
## 选型标准
不以 AI 开发工作量、已有 HA 或容器数量预设优先级。比较使用体验、长期灵活性、稳定性、数据接入及运行效率、实际资源与用户维护。真实公交/驾车的合规免费权限、覆盖与真实数据是两案共同前置条件。
## A：HA 为后端
HA REST / REST command、自动化、模板或自定义集成采集与调度；Local to-do、Shopping list、本地日历或菜单集成管理家庭信息；HA 仪表板、配置向导、备份与更新；hass-eink-dashboard / Paperboard 候选直接渲染。HA 原生更新协调、认证及配置流程成熟（https://contributors.home-assistant.io/core/integrations/fetching-data/），可实现复杂接口；其实体模型、集成 API、共享事件循环和版本兼容是额外约束。阻塞 I/O 或重渲染不能影响 HA（https://contributors.home-assistant.io/core/internals/blocking-operations/）；控制高频 recorder 历史、轮询叠加与认证风险。验证图片端点访问保护及15–30秒级渲染；不将管理凭证放入 Kindle。HA 故障可能导致所有看板业务中断；成熟平台和原生家庭功能是优势。
## B：独立轻量后端 + 按需 HA 对接
同一 NAS 内一个独立容器候选，内部模块化采集、时间调度、校验/限额/退避/缓存、家庭业务、灰度渲染及专用手机管理网页；持久目录独立，JSON 或 SQLite 按需求决定。可复用上游库与开源渲染/Kindle 组件；HA 通过官方 REST/WebSocket 等接口提供智能家居及获准复用的待办，不重复开发智能家居平台。每类家庭数据保持单一权威来源，避免双向同步冲突。核心通勤、天气和显示不依赖 HA 可用；独立容器便于版本固定、资源约束、进程退出重启、升级/回退（https://docs.docker.com/reference/compose-file/services/）。健康检查本身不等于自动恢复卡死，需应用级超时/恢复设计。仍共享 NAS、网络和外部服务，额外容器及自有代码存在维护、安全与故障风险。
## 共同数据层与验收
供应商适配逻辑应尽可能与 HA/独立运行框架解耦，可复用同一合法 API 客户端；统一线路方向、真实多车 ETA、源时间/最新成功采集时间、无车/停运/错误/过期等语义。分时采集、限额、超时、退避、去重、有效期、变化触发及本地离线提示。不得把独立架构或开源集成视为获得授权或免费额度的证据。先验证数据源，再以相同数据样本、频率、渲染尺寸和业务目标比较两案的端到端新鲜度、接口失败恢复、请求数、CPU/RAM/存储、HA 原有服务影响、HA 重启/升级和看板故障隔离及手机操作体验；不必先开发两套完整产品。真实设备不可得时仅做可行测试并注明限制。
## 当前分析意见（非批准）
在强调专用使用体验、独立生命周期、隔离与长期扩展的条件下，B 有结构性优势；A 有原生成熟功能、统一 App/备份和较低额外进程开销优势。不存在已测得的接入成功率、资源或稳定性胜者；最终依据验证及用户确认。两案均优先现有 NAS，不默认新增硬件、付费、常驻浏览器或复杂更新平台。
