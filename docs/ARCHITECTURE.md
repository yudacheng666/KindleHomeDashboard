# 架构建议（未批准）
优先验证单个 NAS 容器：定时采集、缓存、轻量图像渲染、手机管理 HTTP 服务，共用持久目录；采用 Python + Pillow + 轻量 HTTP 框架候选，无常驻浏览器。Kindle 用小型脚本拉取灰度图、校验版本和内容、FBInk 刷新；网络异常保留最后图并显示离线/过期提示（需实机验证）。优先拉取而非开放 Kindle SSH 给所有设备。配置和家庭数据独立持久卷，JSON 原子写入或 SQLite 按复杂度选择。Home Assistant 原生待办及天气优先复用，菜单简单存储。
比较：服务器图片方案便于中文字体、布局及升级，资源与流量随渲染频率变化；网页较易交互但依赖旧浏览器能力与休眠恢复；客户端直接绘制结构化数据可高效局刷，但增加客户端兼容和维护成本。先验证图片路径，必要时仅为关键区域加入轻量本地显示，不提前选定架构。
分离调度、数据有效期、图像变化检测和屏幕刷新；模块失败不阻塞其他模块。断网时本地状态提示不依赖服务器可达；计划测试屏幕残影及开机恢复。客户端仅访问只读显示接口，管理接口需认证，默认 LAN。
初步资源预算（非测量）：轻量单进程加图像库约 50–200 MiB RAM，短时渲染 CPU 峰值需实测；磁盘仅配置、少量图片、受限日志。不预设严格上限；部署前后测空闲/高频/并发家庭使用，观察现有服务。NAS 复用优先；备用板增加电源、系统及维护，只有兼容/负载必要时选用。
更新：优先版本化 Docker 镜像/Compose 手工更新，独立数据卷、备份、健康检查、旧镜像回退；可选低频查询 GitHub Releases 提醒，不默认自动安装，不挂载 Docker socket；客户端低频手工更新，固件不在范围。自动安装需另行安全设计。
