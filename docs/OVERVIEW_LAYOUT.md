# Kindle 单页综合看板

> 状态：**用户已确认屏幕预览；代码已在功能分支实现，自动化测试与 PR 审查待完成；未合并、未发布、未实机验证。**
> 设计基准：Kindle 竖屏约 3:4。实际设备型号及浏览器视口尚未确认，最终字号和物理屏幕适配仍需实机验收。

## 已确认的屏幕结构

严格按竖屏自上而下：

1. 顶部细栏：日期、NAS 时间、唯一设置齿轮。
2. 顶部信息行：左半行公交到站、右半行当前天气，各占约 50%。不显示“公交”“天气”等模块标题。
3. 中间两张地图：上下排列。每张地图左侧为真实地图，右侧为该目的地的真实路线耗时、距离和路况；不显示“驾驶”等模块标题。
4. 底部先菜单、后待办。用图标和日期分组，不显示“菜单”“待办”模块标题。
5. 综合页不显示海报。

视觉采用黑白灰、高对比、少装饰，地图优先使用横向全景比例；所有内容按实际视口自适应，不以缩小到不可读为代价强塞长文本。

## 各区域规则

### 公交（左上，始终显示）

- 最近一辆 ETA 最大字号；下一辆紧凑显示，站数及预计到站绝对时刻按可用数据显示。
- 计划发车与本站 ETA 严格区分；非采集时段、等待、过期、接口限制等状态明确显示，不用时刻表冒充实时到站。
- 沿用现有 NAS 时间、预测、缓存和失效规则；综合页本地读取间隔为 15 秒，与既有公交看板相同，不增加公交上游请求。

### 天气（右上，只显示当前实况）

- 只显示当前地点名称、天气现象、温度、湿度及可用时的体感；有效预警可简短提示。
- **不显示未来几小时、明日或未来几天预报，不显示降雨预测、逐时/逐日曲线。**
- 多地点继续平等轮播，沿用每 120 秒切换；切换不触发供应商请求。
- 新总览 API 只返回 current 与 alerts 两类缓存数据，不向页面发送 forecast sections。

### 地图（中部两张，上下排列）

- 显示前两个已配置目的地；每张地图显示实际静态地图和该目的地返回的路线备选，最快路线突出，其余路线紧凑显示耗时/距离。
- 地图图像请求尺寸改为 600×200 全景比例，以适配 Kindle 地图栏；不增加地图采集频率或请求次数。
- 目的地配置仍最多三个，第三个目的地及所有配置不删除、不覆盖。综合页第二张地图在存在第三个目的地时提供“还有 N 个目的地”入口；点击地图或该入口进入原完整驾驶页面，可查看全部已配置目的地和备选路线。
- 只显示服务实际返回的路线和地图；地图或路线不可用时显示明确状态，不合成虚假地图或耗时。

### 菜单、待办（底部）

- 菜单显示今日和明日餐次，按餐次紧凑排版；综合页摘要仅取今天与明天，不更改完整菜单的日期范围、多用户同步或数据。
- 待办按日期分组，显示最近三项，超出部分提示剩余数量；保留未来日期。只有有管理权限且到期日不晚于 NAS 今天的任务显示低调方框完成按钮，点击仍二次确认；未来任务不允许提前完成。
- 不显示海报；原海报管理及数据保留在设置/管理页面，不删除历史数据。

## 实现约束

- 新增只读 `GET /api/display/overview`，单次汇总现有公交、天气、驾驶、家庭服务的缓存视图；不触发任何上游采集，不新增线程、服务或第三方请求。
- API 仅向总览发送两个驾驶地图组、天气当前实况/有效预警、今天/明天菜单和待办摘要；完整驾驶 API 仍保留三个目的地，家庭管理 API 和权限不变。
- 主页面仅保留一个设置入口。旧的公交/天气/驾驶/家庭详情与管理路径保留兼容；点击地图可进入完整驾驶详情，返回按钮回到综合页。
- 旧 Kindle 浏览器优先 ES5、XHR 和传统 table/block CSS；百分比高度作为 viewport 单位不支持时的回退。页面按约 3:4 竖屏高度分配：顶部约 14%，地图各约 20%，底部菜单约 20%、待办约 26%（另有日期时间栏）。
- 本地缓存视图每 15 秒读取一次；天气地点独立每 120 秒轮播。上游公交、天气、驾驶采集计划、额度及服务运行频率均不改变。
- 模块故障独立降级，其他模块继续显示；认证失败仍按原规则处理。公开测试仅用虚构数据，不提交真实地点、站点、路线、家庭内容或凭证。
